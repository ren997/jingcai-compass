## NovaAPI 数据源评估（https://novaapi.tsgnkj.com/，只读调研）

- 站点是 Vue SPA，文档内容全部内嵌在 `/assets/index-*.js`（约 2MB）里，可直接正则解析出各接口参数/字段；示例代码在 `/assets/java-example.txt` 与 `/assets/python-example.txt`。
- 定位：竞彩 + 北单 + 机构赔率 + 文字直播 + 深度推理，52 个接口。额度 5000 次/日、30 次/分钟，可加额度。
- **鉴权 = Ed25519 非对称签名**：请求头 `X-API-Key` / `X-Timestamp`（毫秒）/ `X-Signature`；签名串为 `apiKey={key}&timestamp={ts}` + 其余 query 参数按 key 升序 `&k=v` 拼接，用 PKCS8 私钥 Ed25519 签名后 base64。JDK 15+ 原生支持，Java 21 可直接实现。
- 关键接口与实测字段：
  - `/nova/sports-lottery/list?date=` — 竞足赛程，matchId/matchNumStr/matchStatus/sellStatus + 竞彩赔率列表（poolCode HAD/HHAD/HAFU/TTG/CRS + goalLine）
  - `/nova/tf/odds` — 赛前机构赔率，参数**全部可选**（idEvent/matchId/bdMatchId 三选一，providerId/marketId 不传即返回全部）；返回 providers→markets→options，option=Home/Draw/Away/Over/Under，含 `line` 盘口线与 `odd`
  - marketId：**4=亚盘让球，5=大小球**，1=胜平负，9=让球胜平负，10=波胆，6/19/26/104=分部玩法，45/56=角球
  - providerId：8=Bet365，4=平博 Pinnacle（10+ 机构）
  - `/nova/tf/odds-history` — 赛前赔率变动，options 带 `points` 时间序列 → 可做 CLV/收盘价，The Odds 免费档做不到
  - `/nova/text/match-results?startDate=&endDate=` — 赛后开奖：sectionsNo1 半场、sectionsNo999 全场、winFlag(H/D/A)、oddsResults（按玩法 code 开奖明细）、hitStatus
- **三个质变**：①赛果是竞彩官方开奖，sectionsNo999 为 90 分钟口径，天然符合亚盘/竞彩结算，规避 The Odds "最终比分含加时"的风险；②matchId 贯穿赛程→机构赔率→赛果，**可整层删掉 match_source_mappings 跨源映射**；③联赛覆盖整个竞彩池（日职/韩K 等），不再受 5 个 sport key 限制。
- 额度测算：一天 50 场，1 次赛程 + 50 次 odds + 1 次赛果 ≈ 52 次/轮；30 分钟一轮 → 约 2500/日，在 5000 限额内；10 分钟一轮会超。
- 风险：无公开价格/条款/SLA/试用，只走微信客服；文档无版本化（契约藏在 SPA 包内，变更不可预警）；数据为二次聚合，授权链不清晰，对"公开展示"仍有合规风险（与 T108 同类问题，换源不等于解决）。
- 待实测确认三项：①providerId/marketId 省略时是否真返回全部机构×玩法；②亚盘 line 是否含 .25/.75 四分之一盘；③赛果可回溯多久（回测需要多赛季）。
- 接入成本估算：新增 `NovaApiProvider`（签名 + 3 端点）约 300 行、`AsianOddsProvider` 映射约 150 行、赛果 Provider 实现约 200 行（把现有两个抛异常方法补实）、配置 + 契约测试约 220 行；核心业务逻辑零改动。

## 比分口径：90 分钟 vs 加时（已从文档确认可区分）

- `/nova/tsd/soccer-events?date=`（足球【新版】→赛事数据→查询赛事列表）返回**四层比分**：`htHomeScore/htAwayScore` 半场、`ftHomeScore/ftAwayScore` **常规90分钟**（文档原文）、`etHomeScore/etAwayScore` 含加时、`penHomeScore/penAwayScore` 点球；外加 `tfStatusShort`（FT/AET/PEN）与 `strStatus`（NS/1H/2H/ET/P/FT/AET/PEN/PST/CANC）。
- **坑**：同接口的 `intHomeScore/intAwayScore` 是"实时累计"，**含加时**，不能用于结算。
- `/nova/text/match-results` 的 `sectionsNo999` 是竞彩官方开奖比分，按竞彩规则即 90 分钟（含伤停补时）。
- `/nova/tf/fixture-detail`（足球【新版】→赛事数据→比赛事件→查询比赛明细）返回 `events[]{seqNo, elapsedMin, extraMin, type(Goal/Card/subst/Var), detail(Normal Goal/Own Goal/Penalty/Missed Penalty)}`，可累加 elapsedMin≤90 的 Goal 独立还原 90 分钟比分，作为第二重校验。
- 结算建议：ft 为主口径 + sectionsNo999 交叉比对；tfStatusShort∈{AET,PEN} 标记进加时并进人工复核；事件流三方对齐。**market_result_facts 需加 score_scope(REGULATION_90/FINAL)**，否则历史事实无法区分口径。

## 阶段 A 范围核实（设计文档有 3 处未覆盖的硬阻塞）

1. **DB 约束挡住新枚举**：`V10` 的 `ck_settlements_market_type CHECK (market_type IN ('HAD','HHAD'))`。加 ASIAN_HANDICAP/ASIAN_TOTAL_GOALS 必须带迁移 —— 而 `asian-model-design.md` 把唯一的 V22 分配给了阶段 E。**阶段 A 需要自己的迁移（V22），阶段 E 顺延 V23。**
2. **`SettlementStatusEnum` 没有 HALF_WIN/HALF_LOSS**，只有 PENDING/HIT/MISS/VOID；DB 也是 `ck_settlements_status IN ('HIT','MISS','VOID')`。四分之一盘拆盘后的半赢/半输**无法表达**。
3. **`settlements` 表根本没有 profit 列**（实体也没有），统计 `StatisticsCalculator:142` 只数 HIT 个数。设计文档 5.2 的「净收益 (price−1)/2、−0.5」语义无处存放。价格本身在 `asian_odds_snapshots` 里有（home_odds/away_odds/over_odds/under_odds），可算，但需要落列。
4. **`pendingMarkets()` 遍历全量 `MarketTypeEnum.values()`**：一旦加两个亚盘枚举，**现有 SPORTTERY 预测也会尝试结算亚盘市场**并因 DTO 不匹配报错。必须改成按 predictionType 取市场集合。这是新增枚举带来的隐藏回归。
5. `MarketSettlementInputDto` 只带 `selectedOutcome(HandicapPickEnum)` + `officialHandicap`，亚盘需要的是 `asianHandicapPick/totalGoalsPick` + 盘口线（从 `asianOddsSnapshotId` 反查 snapshot，或落库到 prediction）。

结论：阶段 A 不是「3 处改动」，实际是 **2 个枚举/迁移 + 1 个 DTO + 2 个计算器 + SettlementWriter 三处改造**，且必须先定「半赢半输与 profit 是否入库」这一决策。

## 阶段 B 跨庄聚合与共识主盘（同日续，收口）

- **核心矛盾与解法**：共识主盘是跨庄算出的线，但 `predictions.asian_odds_snapshot_id` 是**真实行复合外键** `(id, match_id)`，结算只读该行。解法是「**共识定线 + 真实行冻结**」：先用聚合选出决策线，再在报出该线的庄家里挑一条真实快照冻结。这样不改 `predictions` 表、不改 `CanonicalPredictionV3`、不动 `ASIAN_HASH_SCHEMA_VERSION`（改哈希结构会让已发布行重算不一致）。
- **计账价必须是冻结行真实报价，不能用共识公平价**：公平价无法成交，用它算 `settlements.profit` 会让收益脱离实际。这也是「方向取自共识、置信度按冻结行报价」这个不对称的来源——两者**有意不同源**，共识方向 + 该行水位偏高的场次会落到低置信，这是正确的。
- **聚合顺序不可颠倒**：先逐家去水（`p_i = (1/price_i)/Σ(1/price_j)`）→ 取中位数 → 再归一。先中位再去水会把不同抽水率的庄家混在一起算。
- **主盘定义是「最接近 50/50 的线」，不是众数**；线型偏好 `x.5 > x.25/x.75 > 整数` 只在**精确同分 ε=0** 时生效。实证：event 2492881 大小球 2.50 的 imbalance 0.027295 vs 2.75 的 0.024457，只差 **0.002838**，任何非零容差都会选 2.50、偏离平博。
- **白名单按线判定而非按场判定**：该线白名单家数 ≥ `min-whitelist-bookmakers` 才用白名单样本，否则回退全量，并在摘要与指标里标明实际用的哪条路径（否则「回退」会静默发生，事后无法解释为何同一模型两种样本）。
- **取数必须改**：从「每场最新一条完整快照」改为「每场每家每档线的最新报价」（`DISTINCT ON` + 多列 `ORDER BY`）。不改就没有主盘可选——单条快照只能接受写入顺序，等于把「谁最后更新」当主盘。totals 必须按 `total_line` 去重，否则同庄重复计数。

## 阶段 C λ 反解模型（同日续，收口）

- **统一概率口径（本轮核心发明）**：`p_eff = (W + 0.5·HW) / (W + 0.5·HW + 0.5·HL + L)`。由零 EV 定义 `(price−1)(W+0.5HW) = 0.5HL + L` 解出 `1/price` 即上式；半盘（HW=HL=0）、整盘（push 条件化剔除）、四分之一盘（半赢半输半权）共用一条公式，两侧之和恒为 1。市场侧 `1/price` 归一与模型侧必须逐字一致，否则 λ 系统性偏移。
- **三个未经文档、靠实测得出的修正**：
  1. **残差过滤是伪判据**：两方程两未知数是恰定方程组，主盘残差数学上必为 0（实测 1e-16，纯浮点极限）。文档 §4.2 的「残差超阈值判不自洽」等于没有过滤 → 改为**邻线回投校验**（把 λ 投到主盘以外的合格档位比对，阈值 0.0400 由实测最大 3.508% 标定）。
  2. **二维网格改两段一维二分**：`Poisson(λh)+Poisson(λa)=Poisson(λh+λa)`，大小球投影只依赖 λ 总和 → 先由大球概率定总和 S，再由赢盘概率定 λh。根唯一、无平台病态，精度从 1e-4 步长提到 1e-16。
  3. **`max-goals` 16 → 24**：λ 总和 8.0 时 M=16 的截断尾部 3.7e-3 直接击穿「往返误差 < 1e-4」验收；M=24 降到 1.2e-6。概率按行归一，验收依据是「归一后和恒为 1」。
- **缺大小球主盘 → 整场跳过**（`INSUFFICIENT_ASIAN_CONSTRAINTS`），推翻阶段 B 的「降级为单侧方向」。理由：一个方程解不出两个未知数，降级会破坏「同一批草稿每行都有 λ」这条不变量，阶段 D 的 edge 建立在它之上。该判定必须早于冻结行选择。
- **方向改由模型概率投影决定**（`favorsFirstSide`），不再读共识概率：阶段 D 的 edge 由模型概率算，若方向取共识会出现「方向说主队、edge 说客队」的自相矛盾记录。两者在主盘上必然一致（残差 1e-16），故行为不变，只统一来源。置信度阈值**一行未改**。
- **`lineCount == 0` 必须单打标签** `outcome=no-neighbor`：没有邻线 ≠ 校验通过。混为一谈会让校验静默失效时监控无异常、摘要把「无合格邻线」读成「完美自洽」。
- **两套独立实现交叉验证**：Python `Decimal` 原型与 Java 解出的 λ 四位小数完全一致（1.5656/1.2487、1.7638/1.5667、1.7237/1.3792）。邻线最大偏差 2.705%(23 档)/2.057%(21 档)/3.508%(30 档)。
- **Java 比 Python 原型更严格的地方**：`AsianMarketMath.isUsablePrice` 要求**严格大于 1.00**，所以 2492881 的 5.50/7.50 两档（小球恰报 1.00）只剩一家、被正确剔除 → 档数 23 而非预演的 25。这是对的行为，已加单测钉住。
- **已确认的模型局限**：独立泊松在 `±2.5` 以上让球、`5.5` 以上大小球系统性低估尾部，模型概率比市场低 2~4 个百分点（真实比分分布比独立泊松更厚尾）。主盘（−0.25、2.75~3.25）不受影响，故阈值按主盘周围档位标定；收紧到 0.02 会误杀正常场次。

## 阶段 D 选择性发布（同日续，收口）

- **最重要的结论是「门槛不该生效」。** 让球方向的模型概率是把 λ 投影回**同一条主盘线**，而 λ 正是由该线的去水概率反解的，故 `edge = model − market ≡ 0`（残差 1e-16）。通过 `edge >= 抽水分摊 + SAFETY`（让球 2.68%、大小球 3.27%）的场次实测 **0/3**。把 `safety-margin` 调到 0.0001 也不会改善——盈亏平衡点还高出抽水一截。这是「λ 来自市场」的数学后果，不是参数问题。
- **大小球能过门槛的档位是模型误差不是 alpha。** 62 个档位只有 1 档（1.75 低线，+3.51%）能过 3.27% 的门槛；低线（0.50~2.00）偏差三场一致为正、高线（3.50+）一致为负，是独立泊松分布比市场更窄的系统偏差。按它筛选恰好押在模型偏差最大的档位。
- 因此落地为：**σ 硬拦（阈值 0.0200，分市场独立）+ edge 影子门槛（只记录）**。σ 是真信息（跨庄是否互相矛盾），与 λ 的求解方式无关；edge 不是。
- **σ 与置信度是并列否决，不是覆盖。** 输入不同源（σ 来自跨庄共识样本，置信度来自冻结行单行报价）。覆盖会污染 `ConfidenceLevelEnum` 语义，并丧失「HIGH 置信但各家打架」的归因能力。
- **σ 否决必须把方向与置信度成对置空。** `PredictionImportServiceImpl.validateAsianDirectionConfidence` 强制「无方向 ⇒ 无置信度」，只清方向会让整批 `importFile` 抛错回滚。
- **`toPrediction` 改返回 `Evaluation(dto, skipReason)`。** 跳过原因从 v6 起不止一种，调用方原先硬编码 `LOW_CONFIDENCE_ASIAN_MARKETS`，不改则新原因永远记录不到。混合情形（一边低置信、一边 σ 超限）仍归低置信，只有两边都输在分歧上才记 `MARKET_DISPERSION_TOO_HIGH`。
- **指标分母刻意不同**：σ 统计「所有成功反解并选到冻结行的市场」，gate 统计「仍有方向、当前真会发布的市场」。判断能否开闸看 `gate.margin`（`model − 1/price`）分布，不看发布量——`edge` 不含抽水项，无法与边际直接比较。
- **σ 的样本口径不可比**：白名单按线生效，达标时 σ 只反映白名单内部分歧（样本常从十几家掉到两三家，σ 系统性偏小）。指标带 `source` tag，阈值复核必须分 source 做。
- **一个既有测试被新规则推翻**：`derivesDirectionFromModelProjection...` 原夹具（两家 0.479 + 两家 0.61）σ 高达 0.068，本就该被否决——「共识与冻结行方向相左」必然意味着跨庄分歧很大。改为 0.485/0.515/0.525（σ 0.017），保住用例意图。
- **踩坑**：摘要里的版本号是硬编码字面量 `"亚盘 λ 反解 v5"`，改常量不改字面量时，定向单测会以「摘要不含 v6」的形式暴露——比漏改常量好查，但也要记得。

### 三个值得记住的判断

- **10 列统一 `numeric(9,6)`，不用文档的 `numeric(6,5)`。** 生成侧 `PROBABILITY_SCALE = 6`，用 5 位会**静默四舍五入**；精度语义完全交给 CHECK 约束表达。
- **`overProbability` 原先在低置信度下不计算**（只在 `totalsConfidence != LOW` 分支里投影），落库会写 0 而不是真实概率。已改为与方向解耦、恒按冻结线投影。这类「值只在某个分支才算」的写法在新增落库时会系统性变成假数据，后续给其它市场加落库列时要先查这个模式。
- **落库口径统一为首边（主队 / 大球）**，与 `AsianPublishGate.Verdict` 的 `modelProbability`/`marketProbability` 明确区分 —— 后者已按所选方向做过 `1 − p` 换算，直接落库会让方向字段与概率字段互相矛盾。
- **`dispersion` 在共识存在时永不为 null**（`populationStandardDeviation` 对空样本直接抛异常），所以把离散度与概率三元组绑成「同生同灭」是安全的。

### 既有红灯（本轮已修）

`PostgresApplicationIT` 自阶段 A 加 V23 起就是红的（断言 22 个迁移 / 末版本 `"22"`，实际 23）。阶段 A~D 只跑定向 IT，从未跑过这个类。本轮改为 24 / `"24"`，并新增 2 项测试：10 列逐列不可变保护、三组 CHECK 违例。IT 现 9 项在 postgres:16-alpine 全绿。

### 可用性核查（同日晚些时候）

- 纠正一个判断：统计 500 的引爆点**不是**批量发布上线，而是「发布任意一条亚盘预测 + 开赛」。`PredictionLockJob` 自动锁定且不过滤 `prediction_type`，锁定后 `StatisticsCalculator.recordMarket` 必抛，`HomeSummaryQueryServiceImpl:53` 复用同一 summary → **首页与统计页同时 500**。
