### 为什么这个缺口必须在阶段 1 修，而不是留到阶段 5

联赛下拉是前端 `useLeagueOptionsQuery` 从比赛列表里按 `match.leagueId !== null` 反推的。`league_id` 全空 → 下拉只剩「全部联赛」。也就是说**单源一切换，联赛筛选就静默消失**，接口不报错、页面不报错。这不是阶段 5 才出现的问题，而是阶段 1 写库不完整的直接后果；留到阶段 5 会让阶段 2~4 全程跑在一个已坏掉的列表页上。

### 实现

- 新增 `match/service/MatchReferenceDictionary`：按 `name_zh` 取 id、取不到就建，缓存生命周期**限制在一次 `writeAll` 内**（长期缓存会挡住别处新建的字典行）
- `SportteryPoolMatchWriter` 增加 `LeagueMapper` / `TeamMapper` 依赖，`applyMatchFields` 里填 `league_id` / `home_team_id` / `away_team_id`；名字为空时**保留既有归属**而不清空（某次响应缺联赛名不该把已建好的归属抹掉）
- `PersistenceServicesAutoConfiguration` 与 `SportteryPoolSyncMatchWriterTest` 的构造点同步

### 一个刻意的取舍：不加名字唯一索引

`leagues.name_zh` / `teams.name_zh` 目前无唯一约束。加索引能杜绝并发重名，但**多处 IT 用固定名插入 `leagues`/`teams`**（`DataPipelineApplicationIT` 的 `演示联赛`、`PublicMatchQueryApplicationIT` 等），而本机无 Docker 跑不了 IT —— 加约束只会在 CI 才暴露冲突，正是上一轮 `LegacyNameKeyIdentityCleanupMigrationIT` 那种教训。改用「查后插 + 运行内缓存」，靠单实例单任务串行写库兜住重名风险。

### 做了什么

- `NovaApiOddsProvider`：按竞彩 `matchId` 逐场调 `/nova/tf/odds`，一次拿全部机构×玩法，额度=场次数；逐场响应聚合成信封入 raw payload。

### 两个设计判断（与计划有出入，已写进文档）

1. **大小球保留档按「去水概率平衡度」取前 4，不按「报出家数」**。按家数的初版实测会把 `1.5/2.5/3.5/4.5` 排在前面（档位稀疏、每家都报），把平博真实主盘 `2.75` 排掉 —— 主盘会定到 2.5。改用平衡度后三个夹具每场 130/108/156 行，且都包含各庄自己的主盘线。
2. **`AsianOddsPayloadMapper` 未知结构改抛错**。原 `return List.of()` 会让换源问题表现为「同步成功、覆盖率 0%」。

### 修的 bug：`quota_cost` 恒为 0

`ProviderHttpExecutor` 只从响应头解析额度（The Odds API 的 `x-requests-*` 约定）。NovaAPI 实测响应头只有 `nginx / date / content-type / strict-transport-security`，没有任何额度字段 → 额度恒 0 → **5000 次/日上限完全不可见**。

改在 `NovaApiClient.get()` 单点（赛程/赔率/赛果共用），按「首次 1 + 每次重试 1」计。对照证据：同一操作 `id=49 quota_cost=0`（修复前）→ `id=50 quota_cost=13`（修复后）。

这个 bug 只有在真实同步时才会暴露——离线夹具回放走的是 mock，`quotaCost` 由测试自己 new 出来，永远是对的。

### 修正了一条错判据

原验收清单写「每家庄 `count(DISTINCT total_line)` 均 > 1」。这条在「只保留跨庄最平衡 4 档」的设计下必然不成立：单家庄只命中其中 1~2 档是预期结果（实测 betfair/bet365 多数场次 `t_cnt=1`）。正确判据是**按 `(比赛, 让球线)` 聚合后 ≥2 家庄齐全**。判据写错会让人误以为设计坏了。

### 验证明细（可直接复跑的 SQL 结论）

- 可冻结行：13 场每场 14~18 条 `handicap_line` 满足「≥2 家庄 + 四字段齐全」
- 主盘 `total_line` 分布含 `2.25 / 2.75 / 3.00 / 3.25 / 3.50 / 3.75 / 4.00 / 4.50`——**四分之一盘大量出现**，这是「按平衡度选档」修对了的直接证据（按报出家数会只剩 2.5/3.5）
