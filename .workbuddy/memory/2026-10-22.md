## T614 阶段 1 补做：`matches` 字典 ID 填充（分支 `feat/nova-single-source`）

用户要求「继续阶段1」。阶段 1 的三个提交（`bf6d53e`/`db27572`/`3eccb70`/`08b4963`）此前已推送，本轮做的是阶段 1 唯一剩下的缺口。

### 先做了验收核对（真库），确认阶段 1 本身已达标

- `matches` 三个数 `13 | 13 | 13`（总数 / 有外部 ID / 去重外部 ID），与 API 返回 13 场一致
- `match_status` 仅 `SCHEDULED`(10) / `LOCKED`(3)，无 `FINISHED`
- 跨零点 10 场（业务日 10-21、开赛 10-22），与夹具一致 → 证明用的是 `matchStartDate`
- 同一 `external_match_id` 无重复；`data_sync_runs` 两次 `NOVA_API` 均 `SUCCESS 13/13`
- **但 `league_id` / `home_team_id` / `away_team_id` 全为 NULL（13 场 0 填充）**

### 为什么这个缺口必须在阶段 1 修，而不是留到阶段 5

联赛下拉是前端 `useLeagueOptionsQuery` 从比赛列表里按 `match.leagueId !== null` 反推的。`league_id` 全空 → 下拉只剩「全部联赛」。也就是说**单源一切换，联赛筛选就静默消失**，接口不报错、页面不报错。这不是阶段 5 才出现的问题，而是阶段 1 写库不完整的直接后果；留到阶段 5 会让阶段 2~4 全程跑在一个已坏掉的列表页上。

### 实现

- 新增 `match/service/MatchReferenceDictionary`：按 `name_zh` 取 id、取不到就建，缓存生命周期**限制在一次 `writeAll` 内**（长期缓存会挡住别处新建的字典行）
- `SportteryPoolMatchWriter` 增加 `LeagueMapper` / `TeamMapper` 依赖，`applyMatchFields` 里填 `league_id` / `home_team_id` / `away_team_id`；名字为空时**保留既有归属**而不清空（某次响应缺联赛名不该把已建好的归属抹掉）
- `PersistenceServicesAutoConfiguration` 与 `SportteryPoolSyncMatchWriterTest` 的构造点同步

### 一个刻意的取舍：不加名字唯一索引

`leagues.name_zh` / `teams.name_zh` 目前无唯一约束。加索引能杜绝并发重名，但**多处 IT 用固定名插入 `leagues`/`teams`**（`DataPipelineApplicationIT` 的 `演示联赛`、`PublicMatchQueryApplicationIT` 等），而本机无 Docker 跑不了 IT —— 加约束只会在 CI 才暴露冲突，正是上一轮 `LegacyNameKeyIdentityCleanupMigrationIT` 那种教训。改用「查后插 + 运行内缓存」，靠单实例单任务串行写库兜住重名风险。

### 验证

- 单测：后端全量 **732 项**通过，0 失败 0 错误（729 + 新增 3：填入字典 id / 同名只查一次 / 缺失则建行）
- 真库：因 **NovaAPI key 过期**（日卡，`{"code":401,"message":"API密钥无效或已过期"}`）无法在线同步，改用离线夹具回放写库路径
  - 新增一次性脚手架 `backend/src/test/java/com/jingcaicompass/tools/NovaScheduleDictionaryRunTest.java`（未入库，需 `NOVA_VERIFY_DB=true`，`@SpringBootTest` + `local` profile）
  - 回放结果：`success=13 failure=0 snapshots=0`；`league_id`/`home_team_id`/`away_team_id` **13/13/13**
  - 字典规模 `leagues` 7→12、`teams` 38→64，无重名；**再回放一次规模不变**（字典幂等成立）
  - 联赛下拉可枚举 5 个联赛（欧冠 8 场、日职 2 场、西甲/日乙/解放者杯各 1）

### 环境事实（重要）

NovaAPI 的 key 是**日卡**，昨天能用、今天 401。任何依赖真实响应的验证都会随时失效，所以离线夹具 + 回放脚手架是必备的备用验证手段。下次要在线验证前先确认 key 是否已续期。
