## 本轮踩到的四个坑（都会静默放行）

1. **`CHAR(n)` 出库补空格**：`run_key`/`group_key`/`payload_hash` 都要与内存里的十六进制指纹
   逐字比对，读回带空格会让查表静默 miss（表现为「明明有归档却判定未采过」）。
   PG 里 CHAR 无空间也无性能优势，V29 全改 VARCHAR。
   *顺带*：`doesNotContain("CHAR(32)")` 会被 `VARCHAR(32)` 命中，静态断言得用 `(?<!VAR)CHAR\(`。
2. **`@ConditionalOnBean(DataSource)` 必须配自动配置里的兜底 `@Bean`**：该条件在组件扫描期
   恒为 false（DataSource 还没注册），全项目 46 个持久化服务都靠
   `PersistenceServicesAutoConfiguration` 兜底。新服务只加注解不留 `@Bean` → 生产没 Bean；
   只留 `@Service` 不加注解 → 无 DataSource 的测试上下文直接起不来。
3. **`RestClient` 没有 per-call 读超时**：`JdkClientHttpRequestFactory` 的超时是工厂级的，
   所以「历史接口要 60s、实时保持 20s」只能拆两个 `RestClient` bean；
   把全局调宽会让实时同步的卡死检测一起变钝。
4. **手写 `INSERT` 不回填自增 id**：归档落库后要拿 `archive_id` 建 case 外键，
   必须再 SELECT 一次（`ON CONFLICT DO NOTHING` 还得区分「插入了」与「别人先插了」）。

## 回测归档的失败归因（不要合并）

`SUCCESS` / `NO_HISTORY`(404) / `NO_QUOTE_YET`(空序列) 是**终局**，可进负缓存复用；
`RETRYABLE_FAILURE` 下次必重采；`PERMANENT_FAILURE`(400/401/403) 重采只会重复同一个错误。
另有一条实测特例：**HTTP 200 + 响应体 `code=500`** 是上游偶发（换 `idEvent` 即 200），
`ProviderHttpExecutor` 看不到响应体，只能在客户端自己再试一次。

### 四个新坑

1. **`CHAR` 出库补空格会让指纹静默 miss**（已在 V29 改成 VARCHAR）。
   静态断言别写 `doesNotContain("CHAR(32)")`——会被 `VARCHAR(32)` 命中，用 `(?<!VAR)CHAR\(`。
2. **`settleOnce` 的 `WHERE result_status='PENDING'` 返回 0 行是唯一「已结算过」信号**：
   读样本必须只取 `PENDING`（`selectPendingByRunId`），把已结算行读进来只会白跑一遍
   生产计算器，且拿不到「已结算」这个信号。
3. **`total*` 与 `batch*` 两套计数不能合并**：标终态要按「最后一批」的成败判断，
   用累计值会让「中途某批全失败」被后续成功批次掩盖成 SUCCEEDED。
4. **`brierDelta = market − model`，负值是合法结论**：市场 Brier 不是 0.25——走盘记 0.5
   恰好在「市场恒定 0.5」这一腿拿满分 → 0.1875。押次边要取 `1−p`，漏了这一步模型会算成 0.45²。
   负 delta 表示这组样本上模型不如市场，不因「是我们的模型」就取绝对值。
