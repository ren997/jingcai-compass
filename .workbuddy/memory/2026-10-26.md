## 本轮踩到的四个坑（都会静默放行）

1. **`CHAR(n)` 出库补空格**：`run_key`/`group_key`/`payload_hash` 都要与内存里的十六进制指纹
   逐字比对，读回带空格会让查表静默 miss（表现为「明明有归档却判定未采过」）。
   PG 里 CHAR 无空间也无性能优势，V29 全改 VARCHAR。
   *顺带*：`doesNotContain("CHAR(32)")` 会被 `VARCHAR(32)` 命中，静态断言得用 `(?<!VAR)CHAR\(`。
2. **`@ConditionalOnBean(DataSource)` 必须配自动配置里的兜底 `@Bean`**：该条件在组件扫描期
   恒为 false（DataSource 还没注册），全项目 46 个持久化服务都靠
   `PersistenceServicesAutoConfiguration` 兜底。新服务只加注解不留 `@Bean` → 生产没 Bean；
   只留 `@Service` 不加注解 → 无 DataSource 的测试上下文直接起不来。
3. **`RestClient` 没有 per-call 读超时**：`JdkClientHttpRequestFactory` 的超时是工厂级的，
   所以「历史接口要 60s、实时保持 20s」只能拆两个 `RestClient` bean；
   把全局调宽会让实时同步的卡死检测一起变钝。
4. **手写 `INSERT` 不回填自增 id**：归档落库后要拿 `archive_id` 建 case 外键，
   必须再 SELECT 一次（`ON CONFLICT DO NOTHING` 还得区分「插入了」与「别人先插了」）。

## 回测归档的失败归因（不要合并）

`SUCCESS` / `NO_HISTORY`(404) / `NO_QUOTE_YET`(空序列) 是**终局**，可进负缓存复用；
`RETRYABLE_FAILURE` 下次必重采；`PERMANENT_FAILURE`(400/401/403) 重采只会重复同一个错误。
另有一条实测特例：**HTTP 200 + 响应体 `code=500`** 是上游偶发（换 `idEvent` 即 200），
`ProviderHttpExecutor` 看不到响应体，只能在客户端自己再试一次。

## 整链首次在真实库跑通 + 三个首跑缺陷（23:42 之后）

打开 `app.tasks.backtest-run.enabled=true` 后跑真实区间（`2026-10-20` 一天、10 场、2 个参数组），
连续废掉三个 run 才出结果。**三个缺陷全部只在「默认关闭的开关打开」或「真实库真有数据」
时才触发**，单测与 CI 一个都覆盖不到。

### 缺陷 1：`initialDelayString` 不认 Spring Boot 简写时长

`initialDelayString = "${app.backtest.worker.initial-delay:60s}"` → `NumberFormatException:
For input string: "60s"`，`Encountered invalid @Scheduled method 'poll'`，应用直接起不来。
而该 bean 只在 `app.tasks.backtest-run.enabled=true` 时才创建 —— **默认配置下永远发现不了**。
`fixedDelayString` 认 `30s` 这种写法，`initialDelayString` 只接受毫秒或 ISO-8601，**两条解析路径**。

修法：新增 `BacktestSchedule`（`@Component("backtestSchedule")`）暴露两个 `xxxMillis()`，
注解写 `#{@backtestSchedule.pollIntervalMillis()}`，与其余八个 job 的 `SyncTaskSchedule` 同形态。
`BacktestRunJobTest` 断言注解文本本身，才拦得住「看起来一样、行为不同」的回退。

### 缺陷 2：`processed_match_count` 被两个阶段各加一次

10 场变 20 场 → `ck_backtest_runs_counts`（`processed <= total`）`DataIntegrityViolationException`。
**撞在「归档成功、判定开始」那一刻，看起来像判定坏了。**
第一次只改了 `batch % batchSize` 分支内的调用，漏了循环外**末尾那次 flush** → 第二次仍撞。
最终拆成 `flushArchiveProgress` / `flushEvaluationProgress`，后者**签名里没有 processed 参数**，
让这个错误在编译期就写不出来，而不是靠注释提醒。

顺带：无增量的 flush 原来直接 `return`，心跳跟着停。判定阶段整批被跳过时它是唯一存活证据，
心跳一停重启自愈会把还在跑的 run 判成 `INTERRUPTED`。改为 `runMapper.touchHeartbeat(...)`。

### 缺陷 3：`@Select` 注解查询不应用 `@TableField(typeHandler)`

最隐蔽的一个。归档行为 `bookmaker_count=6`、`point_count=878`、`fetch_status=SUCCESS`，
但 case 全部 `decisionStage=MISSING_ROWS`、`frozen*=null`、`skipReason=MISSING_CONFIRMED_ASIAN_MARKET`。
**归档状态、点数、庄家数全部正常，最像「这段时间上游没开价」。**

定位：先用 `SnapshotDebug` 把真实载荷直接喂生产 `OddsHistorySnapshotBuilder` →
`rows=167 handicapQuotes=57 empty=false`，证明切片器没问题；问题在 `objectMapper.valueToTree(
archive.getPayload())` 拿到空 Map。
根因：`@TableName(autoResultMap = true)` 生成的 resultMap **只被 MyBatis-Plus 自己拼的 SQL 使用**，
`@Select` 走原生映射，`Map<String,Object>` 掉到默认 handler，读回空 Map（不抛错、不触发 fallback）。
修法：`selectPayloadTextById` 取 `payload::text` + `objectMapper.readTree`。
