## 「已结算只有一半」不是算错，是两个量纲并排

用户看 run 6 指标表第一反应是「80 场为什么只算了一半」。查清后是展示歧义：
**「样本」是场次，「已结算」是腿**，两者分母不同，`settledCount / caseCount` 没有意义。


`-4.605 / 40 = -11.51%`，与表上数字对得上——**算法没问题，是表头没写单位**。

## 参数组 baseline / tight 到底是什么

用户连问两轮「这两个词什么意思」，说明页面自解释性不够。查清后：

`baseline` / `tight` **是创建回测时自己填的标识（`groupKey`），没有固定含义**，
真正定义它的是四个阈值（HIGH / MEDIUM 各一对）：

| 阈值 | baseline | tight | 物理含义 |
|---|---|---|---|
| `highConfidenceMargin` | 0.100 | 0.080 | `1/主+1/客−1`，庄家抽水率上限 |
| `highDirectionSignal` | 0.075 | 0.090 | `\|1/主−1/客\|/(1/主+1/客)`，方向倾斜度下限 |
| `mediumConfidenceMargin` | 0.160 | 0.120 | 同上，次级门槛 |
| `mediumDirectionSignal` | 0.025 | 0.040 | 同上，次级门槛 |

**实测（run 6 全 160 条样本，分两页取——`pageSize` 上限 100）：阈值只决定「发不发」，
不决定「判什么」**：

```
让球    baseline 25 场 → tight 18 场   tight ⊆ baseline，方向不一致 0 场
大小球  baseline 21 场 → tight 11 场   同样是子集，方向不一致 0 场
INFEASIBLE（λ 解不出）两组都是 44 场 —— 与阈值无关
BOTH_MARKETS_REJECTED  4 → 11 场（收紧后多的 7 场）
```

收紧后 ROI 反而略差（−11.51% → −12.98%），说明「只做最明确的场次」在这批数据上没好结果。
但 29 条腿样本太小，不能当结论。

**踩坑**：第一次统计时 `pageSize=200` 被后端截到 100，只拿到 baseline 80 + tight 20，
差点得出「tight 只有 20 场」的错误结论。**分页接口一律核对 `total` 与记录数是否相等。**

## 流程教训：`tsc | tail` 判断不了失败

一直在用 `npx tsc -b 2>&1 | tail -10 && echo TSC_OK`，但**管道的退出码是 `tail` 的**，
`&&` 永远成立。这次改成 `npx tsc -b > /tmp/tsc.log 2>&1; echo "exit=$?"` 才看清
那个 `TS2739` 类型错误。以后前端三项检查一律重定向 + 检查 `$?`。

## 两个 `@ConditionalOnBean` 的坑，一次踩全

第一版照抄 `AdminSportteryResultSyncServiceImpl` 写了 `@ConditionalOnBean(DataSource.class)`，
启动直接 `No qualifying bean of type AdminSportteryPoolBackfillService`。
原因是**该注解在组件扫描阶段按同包字母序求值**：`AdminSportteryPoolBackfill...` 排在
`AdminSportteryResultSync...` 之前，扫描到它时自动配置的 DataSource 还没注册。
去掉注解后 local 能起，但 `mvn -o test` 冒出 3 个 Error——test profile 排除了
`DataSourceAutoConfiguration`，无条件创建又因 `SportteryPoolSyncService` 缺失把整个
ApplicationContext 拖垮。

最终用 `ObjectProvider` 惰性取：无库时端点存在并抛 `DATA_SOURCE_UNAVAILABLE`，
和 `NoPersistenceAdminAutoConfiguration` 的 NoOp 语义对齐。单测 6 项（含这一条）。

## Hikari 默认值扛不住远端库

两次长任务失败都不是逻辑错误：`Connection is not available ... 30036ms (total=9, active=0, idle=9)`
和 `Connection reset`。远端 PG 掐掉空闲连接，而 Hikari 默认 `max-lifetime=30min`、
心跳关闭，于是取到已死的连接。`application-local.yml` 补 `keepalive-time=120s`、
`max-lifetime=300s`、`idle-timeout=180s`、`connection-timeout=10s`。
**`active=0` 却拿不到连接，就是在用死连接，不是池子太小。**
