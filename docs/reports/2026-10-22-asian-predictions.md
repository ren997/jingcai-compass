## 三、必须说明：13/13 全小球不是模型观点，是冻结行选取的缺陷

这批最刺眼的特征是**13 场大小球全部 `UNDER`、全部 `HIGH`**。如果把它当成模型观点，会得出「模型一致看空全欧战进球」的错误结论。实际原因是链路上一处可定位的缺陷。

### 现象

13 场每一条 `analysis_summary` 都带着同一句括号注记：**「该行未报主盘线」**。逐条对比冻结行的大小球线与跨庄共识的大小球主盘线：

| 场次 | 大小球主盘 | 冻结行判定线 | 偏差 |
|---|---|---|---|
| 周四001 | 2.75 | 3.25 | **+0.50** |
| 周四002 | 2.75 | 3.00 | **+0.25** |
| 周四003 | 3.00 | 3.50 | **+0.50** |
| 周四004 | 3.00 | 3.25 | **+0.25** |
| 周四005 | 3.50 | 4.00 | **+0.50** |
| 周四006 | 2.75 | 3.25 | **+0.50** |
| 周四007 | 2.75 | 3.25 | **+0.50** |
| 周四008 | 3.25 | 3.50 | **+0.25** |
| 周四009 | 3.25 | 3.75 | **+0.50** |
| 周四010 | 3.25 | 3.50 | **+0.25** |
| 周四011 | 3.25 | 3.50 | **+0.25** |
| 周四012 | 2.75 | 3.25 | **+0.50** |
| 周四013 | 2.25 | 2.75 | **+0.50** |

**13/13 全部高于主盘线，无一例外，且偏差只有 `+0.25` 与 `+0.50` 两种取值**。这不是随机选档能产生的分布。

### 成因（已定位到行号级）

1. 交叉积落库：同一家庄的同一让球线会展开成「让球线 × 大小球档」多行。以周四001 的 pinnacle 让球 `+0.50` 为例，四档连续写入，`id` 与 `captured_at` 同步递增：

   | id | total_line |
   |---|---|
   | 174 | 2.50 |
   | 175 | 2.75 ← **主盘线** |
   | 176 | 3.00 |
   | 177 | 3.25 |

2. `AsianOddsSnapshotMapper.selectLatestHandicapLinesByMatchIds` 用
   `DISTINCT ON (match_id, provider_code, bookmaker_code, handicap_line)`
   配 `ORDER BY ... captured_at DESC, id DESC` 取「每家每档让球线的最新报价」。同一让球线的四行 `captured_at` 几乎相同、`id` 递增，于是**每组只留下 `id` 最大的一行 = `total_line` 最大的一档**。本场留下 `id=177 / 3.25`。

3. `AsianFreezeSnapshotSelector.select` 在这批已去重行里挑冻结行。`freezable()` 只要求 `handicapLine == 共识主盘线`，此时**每家只剩一行候选**，排序键 `alignedWithTotalsLine`（该行大小球线是否等于大小球主盘）永远为 `false`，**形同虚设**。最终冻结行必然是「该家让球主盘上最大的那个大小球档」。

4. 方向投影：λ 由**主盘**（让球主盘 + 大小球主盘 2.75）反解，但方向要投影回**冻结行**的线——这条线是 3.25。线抬高了 0.5 球，`p(大球)` 自然被压低，于是判 `UNDER`。13 场全部如此，就出现 13/13 全小球。

### 后果

- **方向系统性偏向小球**，与本批实际市场共识无关。10-21 那批用 `THE_ODDS_API` 只出现 5/10 小球，且判定线与主盘线的偏差不是单向的；换 NovaAPI 单源后交叉积形态变了，缺陷才被放大到 13/13。
- **`edge_over` 全部非零**（`+0.0015` ~ `+0.0188`），但那不是 alpha，是「投影线 ≠ 反解线」的形状偏差。让球方向之所以 `edge ≡ 0`，正是因为它投影回的线就是主盘线。
- **结算口径会被抬高**：按冻结行的 3.25/3.50 判小球，比市场真实主盘 2.75/3.25 更容易赢。这会让回测看起来偏好，属于口径污染而非模型能力。
- **本批已无法修正**：13 条均已 `PUBLISHED`，`protect_published_prediction()` 触发器禁止改内容；且 00:45 开赛，重新生成发布也来不及。这批的**实际意义仅限于验证链路跑通**，不能作为模型观点引用。

### 修复方向（已于当晚实施，见第五节）

冻结行选择应当使用**完整交叉积行集**（按 `(match, provider, bookmaker, handicap_line, total_line)` 去重），而不是复用让球聚合的去重结果。让球聚合本身不受影响——同一家同一让球线的四档让球赔率完全相同（实测 pinnacle `0.50` 四档均为 `2.03/1.88`），聚合器按 `(bookmaker, line)` 覆盖后结果一致。**被污染的只有冻结行选择这一步。**

## 四、口径与限制（必读）

1. **概率口径是首边（主队赢盘 / 大球）。** 表中已按发布方向换算：客队方向取 `1 − p`，小球方向取 `1 − p`。`edge` 同理。落库字段本身仍是首边口径。
2. **v6 的模型概率就是从这两个市场的去水概率反解出来的。** 让球主盘上 `模型概率 ≡ 市场概率`，所以 6 个已发布让球方向的 `edge` 全为 `0.0000`。这是「本版本没有独立于市场的信息」的量化证据，不是 bug。
3. **盈亏平衡 = 1 / 该方向真实水位**，含抽水。**这批 13 个大小球方向的盈亏余量全部为负**（`-0.0037` ~ `-0.0279`），即按 v6 自己的影子标准，没有一个方向具备正期望。不要因为「13 场一致看小球」就当成强信号。
4. **置信度与方向来源不同**：方向取自模型概率，置信度按冻结行真实报价计算。已发布的 6 个让球方向流水位都在 `1.83~1.90` 一侧，未发布的多是 `1.93~1.98` 的平衡盘——**置信度衡量的是「这家报价是否明确到可交易」，不是「模型有多确信」**。
5. **σ 阈值 `0.0200` 是硬拒。** 周四001 让球 `σ = 0.022398` 被直接否决，周四012 `σ = 0.019710` 恰好通过。这批大小球 σ 全部远低于阈值（最大 `0.009286`）。
6. **样本只有 13 场且全部未开赛**；加上第三节的缺陷，这份记录**不能用来评估准确率或收益**。结算结果见第六节。

1. **`edge` 两边现在都恒为 0。** 重算里 10 条的 `模型概率` 与 `市场概率` 逐位相等（例：周四001 两侧均 `0.526254`）。原来那段「`edge_over` 非零」不是 alpha，是「投影线 ≠ 反解线」的形状偏差；判定线对齐主盘后它自然归零。**这意味着大小球方向从此和让球方向一样，只是市场共识的复述。**
2. **方向翻不翻，只看主盘那一档偏哪边。** 周四001 从 3.25 降到 2.75，`p(大球)` 从 0.4121 升到 0.5263，方向就从「小球」翻成「大球」——变的不是模型，是线。
3. **3 场直接不出预测，是修复的必然结果，不是退步。** 主盘那一档的水位都在 `1.85~1.95` 的平衡区（旧数据 `1.56~1.75` 的偏斜水位是线被抬高造成的），置信度判 LOW → 两个市场都没有可发布方向 → 整场跳过。**旧批次看起来「13 场都有方向」，是因为线错了。**
4. **单边方向（只有让球、没有大小球方向）现在也能合法发布。** 那 4 条 `ou=null` 的行里 `model_over_prob` / `market_over_prob` / `totals_dispersion` 全部非空，十列齐全 → 能算出 v4 哈希。10-21 那批 `id=41`/`48` 因为缺四列而永远发不出去的老问题，在这个形态下不会复发。

### 为什么没有「重新发布」

- 13 条已 `PUBLISHED`，`protect_published_prediction()` 触发器禁止改内容；
- 首发场次 00:45 开赛，发布服务同时校验「发布截止时间」与「比赛状态为 SCHEDULED/LOCKED」，重算出的新版本（v2 DRAFT）不会被自动发布候选选中（该查询排除已发布场次）。

所以这一批实际开奖结算仍按**旧判定线**（3.25/3.50 等）判定。**结算时会显得比真实主盘更容易赢**，回测统计应把这 13 条单独标注或剔除。**从下一业务日起，自动发布链路产出的是第五节这一套口径。**

重算脚本为 `backend/src/test/java/com/jingcaicompass/tools/RecalcTotalsLineRunTest.java`（约定不入库），用 `RECALC_RUN=true` 复跑，只读、不写任何预测行。
